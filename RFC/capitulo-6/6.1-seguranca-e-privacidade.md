# 6. Segurança e Privacidade

Esta seção descreve as medidas de segurança adotadas no sistema, abordando tanto aspectos técnicos de proteção da aplicação quanto considerações sobre privacidade dos dados dos usuários. A relevância dessas preocupações é amplificada pelo contexto do C$Diagrams: diagramas de arquitetura de software — mesmo em contexto acadêmico — podem conter informações sensíveis sobre topologias de rede, integrações com sistemas externos e estruturas internas de bancos de dados. Garantir que essas informações sejam acessíveis apenas ao usuário proprietário é, portanto, um requisito central do sistema.

---

## 6.1 OWASP Top 10

O OWASP Top 10 é uma referência consolidada que lista as categorias de vulnerabilidades mais críticas em aplicações web. A seguir, são apresentadas as categorias aplicáveis ao C$Diagrams, com as respectivas contramedidas adotadas.

**Tabela 9 — Categorias OWASP Top 10 aplicáveis ao C$Diagrams**

| Categoria OWASP | Aplicabilidade | Contramedida adotada |
|---|---|---|
| A01 - Broken Access Control | Alta | Isolamento de dados por `user_id` em todas as queries; middleware de autenticação JWT em todas as rotas protegidas |
| A02 - Cryptographic Failures | Alta | Senhas armazenadas com bcrypt; criptografia em repouso no banco de dados (ver seção 6.3) |
| A03 - Injection | Média | Uso de queries parametrizadas no repositório de dados; nunca concatenação direta de input em SQL |
| A05 - Security Misconfiguration | Média | Variáveis sensíveis (chaves JWT, credenciais do banco, API key do Gemini) armazenadas como variáveis de ambiente, nunca no repositório |
| A07 - Identification and Authentication Failures | Alta | Tokens JWT com expiração definida; limite de tentativas de login; confirmação de e-mail no cadastro |
| A09 - Security Logging and Monitoring Failures | Baixa | Registro de eventos críticos (falhas de autenticação, erros de acesso) nos logs da aplicação |

As categorias não listadas (A04, A06, A08, A10) foram avaliadas como de baixa aplicabilidade ao escopo atual do sistema, dado que o C$Diagrams não utiliza componentes de terceiros no frontend além das bibliotecas listadas na seção 5.4, não expõe interfaces de administração e não processa uploads de arquivos arbitrários.

### 6.1.1 Broken Access Control

Esta é a categoria de maior risco para o C$Diagrams, dado o caráter sensível dos diagramas de arquitetura armazenados. Um diagrama pode expor detalhes como nomes de serviços internos, estruturas de banco de dados, endereços de APIs e integrações com sistemas externos — informações que não devem ser acessíveis a outros usuários da plataforma.

A contramedida central é o **isolamento de tenants por `user_id`**: todas as operações de leitura, atualização e exclusão na camada de repositório incluem obrigatoriamente o `user_id` extraído do token JWT como filtro. Isso garante que mesmo uma requisição autenticada com um ID de projeto válido, mas pertencente a outro usuário, seja rejeitada. Essa abordagem está alinhada com os requisitos RNF05 e RN02 definidos na seção 2.

Adicionalmente, o middleware de autenticação valida o token JWT em todas as rotas protegidas antes de qualquer lógica de negócio ser executada, impedindo o acesso não autenticado.

### 6.1.2 Cryptographic Failures

As senhas dos usuários são armazenadas exclusivamente como hash gerado pelo algoritmo bcrypt, com salt automático. Nenhuma senha é armazenada em texto plano ou em formato reversível. O processo de autenticação compara o hash armazenado com o hash da senha fornecida, sem jamais recuperar a senha original.

Os tokens JWT são assinados com uma chave secreta armazenada como variável de ambiente, com tempo de expiração configurado. Tokens expirados são rejeitados pelo middleware de autenticação.

### 6.1.3 Injection

Toda interação com o banco de dados é realizada por meio de queries parametrizadas, eliminando a possibilidade de SQL Injection. Isso se aplica também às operações sobre colunas `jsonb`, onde os dados do diagrama são serializados como JSON antes de serem passados como parâmetro — nunca interpolados diretamente na query.

## 6.2 Autenticação e Autorização

O sistema adota autenticação baseada em **tokens JWT (JSON Web Tokens)**, padrão consolidado para APIs REST stateless. O fluxo de autenticação funciona da seguinte forma:

1. O usuário fornece e-mail e senha no formulário de login
2. O backend valida as credenciais comparando o hash bcrypt armazenado
3. Em caso de sucesso, um token JWT assinado é retornado ao frontend
4. O frontend inclui o token no header `Authorization: Bearer <token>` em todas as requisições subsequentes
5. O middleware de autenticação valida a assinatura e a expiração do token a cada requisição

A **autorização** é tratada no nível da camada de repositório, garantindo que o `user_id` do token seja sempre utilizado como filtro nas operações de dados — não apenas como verificação de autenticidade, mas como delimitador do escopo de acesso.

## 6.3 Criptografia de Dados em Repouso

Conforme definido no RNF06, os dados dos usuários devem ser armazenados de forma criptografada em repouso. No contexto do C$Diagrams, isso se aplica principalmente ao banco de dados PostgreSQL hospedado no Railway.

O Railway habilita criptografia em repouso por padrão em todos os volumes de dados, utilizando AES-256 a nível de infraestrutura. Isso significa que os arquivos físicos do banco de dados — incluindo as tabelas de usuários, projetos e os documentos `jsonb` com o estado dos diagramas — são armazenados de forma criptografada no disco, sem necessidade de configuração adicional na aplicação.

É importante distinguir os dois tipos de proteção aplicados:

- **Criptografia em repouso (encryption at rest):** garante que os dados sejam ilegíveis caso o meio físico de armazenamento seja comprometido. Provida pela infraestrutura do Railway.
- **Criptografia em trânsito (encryption in transit):** garante que os dados não sejam interceptados durante a comunicação entre frontend, backend e banco de dados. Provida pelo uso de HTTPS/TLS nas comunicações externas e pela conexão SSL entre backend e PostgreSQL no Railway.

Juntas, essas duas camadas garantem que os diagramas de arquitetura dos usuários — que podem conter informações sensíveis sobre seus sistemas — estejam protegidos tanto durante o armazenamento quanto durante a transmissão.

## 6.4 Privacidade e LGPD

Esta seção descreve como o C$Diagrams trata os dados pessoais dos usuários, em conformidade com a Lei Geral de Proteção de Dados (Lei nº 13.709/2018 — LGPD).

### 6.4.1 Dados Coletados

O sistema coleta apenas os dados estritamente necessários para o funcionamento da plataforma:

| Dado | Finalidade |
|---|---|
| Nome | Identificação do usuário na plataforma |
| E-mail | Autenticação, recuperação de senha e comunicações transacionais |
| Senha (hash) | Autenticação segura — armazenada exclusivamente como hash bcrypt |
| Projetos e diagramas | Conteúdo criado pelo usuário, armazenado para possibilitar edição e recuperação futura |
| Data de criação e atualização | Controle de integridade e auditoria interna |

O sistema **não coleta** dados de localização, dados de navegação, informações de pagamento, nem realiza rastreamento comportamental.

### 6.4.2 Armazenamento e Retenção

Os dados são armazenados em banco de dados PostgreSQL hospedado no Railway, com criptografia em repouso conforme descrito na seção 6.3. O acesso ao banco de dados é restrito ao backend da aplicação por meio de credenciais armazenadas como variáveis de ambiente.

Os dados são retidos enquanto a conta do usuário estiver ativa. A definição de uma política de expiração automática para contas inativas está prevista para versões futuras do sistema.

### 6.4.3 Direitos do Usuário e Solicitação de Remoção

Em conformidade com os artigos 17 a 22 da LGPD, o usuário tem direito ao acesso, correção e exclusão de seus dados pessoais. No C4Diagrams, esses direitos são exercidos da seguinte forma:

- **Exclusão de projetos e diagramas:** o próprio usuário pode excluir seus projetos diretamente pela interface da aplicação. A exclusão de um projeto implica na remoção permanente de todos os diagramas vinculados, conforme RN05.
- **Exclusão de conta e dados pessoais:** solicitações de exclusão completa da conta — incluindo nome, e-mail e todos os dados associados — devem ser encaminhadas por e-mail ao responsável pelo sistema. Após a solicitação, os dados serão removidos permanentemente do banco de dados em até 30 dias.

Vale observar que, no contexto acadêmico atual do projeto, o responsável pelo tratamento dos dados é o próprio desenvolvedor. Em um cenário de implantação comercial, seria necessário formalizar a figura do Controlador e do Operador de dados conforme a LGPD, bem como publicar uma Política de Privacidade acessível aos usuários.
