# 7. Planejamento do Projeto

Esta seção apresenta os principais marcos de desenvolvimento do C4Diagrams, organizados em fases incrementais alinhadas aos requisitos funcionais definidos na seção 2. Os prazos são expressos em semanas relativas ao início do desenvolvimento.

| Marco | Descrição | Requisitos cobertos | Prazo estimado |
|-------|-----------|---------------------|----------------|
| M1 | Setup do ambiente, estrutura do repositório e infraestrutura de qualidade: configuração do banco de dados, prova de conceito do canvas com React Flow, pipeline CI/CD com GitHub Actions, integração com SonarCloud, Wiki do repositório e board Kanban no GitHub Projects | Infraestrutura base | Semanas 1–2 |
| M2 | Módulo de autenticação completo: cadastro, login e recuperação de senha — desenvolvido com TDD | RF01, RF02, RF03 | Semanas 3–4 |
| M3 | Gerenciamento de projetos e editor base: criação, listagem, edição e exclusão de projetos; drag-and-drop de elementos no canvas — desenvolvido com TDD | RF04–RF11 | Semanas 5–7 |
| M4 | Estrutura C4 completa: suporte aos 4 níveis, validação estrutural e assistente de IA com Google Gemini — desenvolvido com TDD | RF12–RF17 | Semanas 8–10 |
| M5 | Funcionalidades complementares: exportação (PNG, PDF, JSON), modo textual e Undo/Redo — desenvolvido com TDD | RF18–RF23 | Semanas 11–12 |
| M6 | Revisão de cobertura de testes, refinamento de UX, atualização da Wiki e documentação final | — | Semanas 13–14 |

O desenvolvimento segue uma abordagem incremental, priorizando a entrega de valor funcional a cada marco. As funcionalidades de maior complexidade técnica — assistente de IA e modo textual — foram posicionadas após a consolidação da base do editor, reduzindo o risco de retrabalho.

A prática de **TDD (Test-Driven Development)** é adotada desde o M2, garantindo que cada funcionalidade seja especificada por testes antes da implementação. O M6 não introduz testes como etapa isolada, mas revisa a cobertura acumulada e endereça gaps identificados ao longo do desenvolvimento.

A infraestrutura de qualidade estabelecida no M1 inclui:

- **CI/CD via GitHub Actions** — pipeline automatizado de lint, testes e deploy contínuo para GitHub Pages (frontend) e Railway (backend) a cada push na branch principal.
- **SonarCloud** — análise estática de código integrada ao pipeline, com relatórios de qualidade, cobertura de testes e detecção de vulnerabilidades. Gratuito para repositórios públicos.
- **Wiki do GitHub** — documentação técnica do projeto mantida junto ao repositório, cobrindo decisões de arquitetura, guia de contribuição e instruções de setup.
- **GitHub Projects (Kanban)** — gerenciamento de tarefas integrado ao repositório, com rastreabilidade entre issues, pull requests e marcos de desenvolvimento.

Como diretriz de implementação, o código deve seguir os princípios de **SOLID** e **Clean Code**, promovendo legibilidade, manutenibilidade e baixo acoplamento entre os módulos do sistema.
